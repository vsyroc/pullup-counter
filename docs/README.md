# План разработки счётчика подтягиваний

Счётчик — Telegram-бот на Go. Пользователь выбирает неделю в личном чате и может записывать подходы лично или в группе. Бот ведёт отдельный дневник для каждого участника. Бот присылает утром тихое сообщение с планом выбранной недели. В плановой тренировке первая запись открывает день, а заполнение пяти позиций завершает план и отключает напоминания. Дополнительные подходы входят в итог дня. В день отдыха пользователь записывает свободные подходы. Даже если подходы растянулись за полночь, тренировка относится к дате старта.

[Программа на 30 недель](program.md) перенесена из вложения заметки Obsidian `[[План]]`. В репозитории есть точка входа на Go и команды `make run` и `make build`.

## Стек и размещение

Один Go-бинарник работает на домашнем Orange Pi Zero 3 с 4 ГБ памяти под управлением systemd. Бот получает обновления Telegram через long polling. Дневники и расписание хранятся в локальной базе SQLite. Для деплоя запланированы сборка бинарника на GitHub-hosted runner и доставка на Orange Pi напрямую по SSH.

## Ветки и релизы

В этом репозитории основная ветка называется `master`. Создаём ветку каждой фичи от актуальной `dev`, вливаем фичу через PR в `dev`, затем переносим готовые изменения в `master` одним PR из `dev`.

CI запускает `go test ./...` на каждом push в `dev` и основную ветку, а также на PR в эти ветки. Для соблюдения порядка слияний на GitHub нужно включить защиту основной ветки: требовать PR и успешную проверку `test`. Workflow также распознаёт имя `main` на случай переименования основной ветки.

### Как выпустить версию

Номер версии храним только в Git-теге формата `vMAJOR.MINOR.PATCH`. В `master` может накопиться несколько слияний из `dev`. Тег ставим, когда выбираем конкретный коммит для установки на Orange Pi.

Первый рабочий выпуск обозначаем `v0.1.0`. Если следующим выпускаем исправление, ставим `v0.1.1`. Если в выпуск вошла новая возможность, например напоминания, ставим `v0.2.0`. Версию `v1.0.0` оставляем для первого стабильного выпуска.

После слияния PR из `dev` в `master` находим в GitHub Actions успешный запуск CI для нужного коммита и копируем его SHA. Для первого выпуска выполняем команды ниже, подставив этот SHA вместо `<SHA>`.

```bash
git fetch origin master
git tag -a v0.1.0 <SHA> -m "Первый рабочий выпуск счётчика"
git push origin v0.1.0
```

Опубликованный тег всегда указывает на исходный коммит. Для исправлений выпускаем новый тег. Сейчас публикация тега фиксирует версию в GitHub. Автоматический деплой по тегу запланирован в [эпике 0](roadmap/00-ci-cd.md).
